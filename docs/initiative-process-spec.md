# אפיון תהליך הובלת יוזמה · מחנכי עיר

מסמך זה מאפיין את החלק "הובלת יוזמה" (מודול 2) באפליקציה. הבסיס הוא אפליקציית **מחנכי עיר מפצחים כאב בטן** (פרוטוקול הגדרת בעיה לעבודה בקבוצות, מעוז), שהפכה למרחב העבודה של כל צוות. המסמך מתאר מה בנוי היום (✔) ומה מוגדר ועוד לא נבנה (◻).

## 1. עקרונות

1. **צוות אחד, יוזמה אחת.** משתתפים מתארגנים בצוותים בתוך הקבוצה. לכל צוות מרחב עבודה משלו ונתונים משלו.
2. **חוט שדרה אחד.** כל שלב נשען על התוצר של הקודם, ולא מתחיל מדף ריק: שאלה מובילה ← תופעה ← עץ ← נתיב קריטי ← הגדרת בעיה ← רעיון לפיילוט ← תוכנית ← פיצ׳.
3. **הזמן להגדרת הבעיה הוא ההשקעה.** שלב 1 הוא הארוך והמוקפד ביותר, ושער היציאה ממנו הוא הגדרת בעיה חדה עם הנחות יסוד, כפי שקובע הפרוטוקול.
4. **אדם אחד מקליד, הצוות מסייע.** ממלא.ת אחד.ת כותב.ת, והאחרים רואים בזמן אמת, שולחים הצעות ומצביעים.
5. **המנהל.ת רואה ולא מנהל.ת את העבודה.** מנהל.ת הקבוצה עוקב.ת אחרי התקדמות כל צוות ויכול.ה להיכנס למרחב שלו לצפייה והצעות, אבל לא מחליט.ה במקומו.

## 4. שלב 1 בפירוט: פרוטוקול הגדרת בעיה

חלק ראשון, פורסים את המצב. חלק שני, מתמקדים.

| מסך | מה הצוות עושה | נתונים שנוצרים | מתי נחשב הושלם |
|---|---|---|---|
| הכנת המפגש | כותבים את השאלה המובילה, בוחרים אחראי.ת זמנים | `question`, `timeUid` | יש שאלה מובילה |
| 1 · ניסוח תופעה | צרכים, פערים בין הרצוי למצוי, ניסוח תופעות קונקרטיות ובחירת אחת | `needs`, `gaps`, `phens`, `chosenPhen` | נבחרה תופעה |
| 2 · עץ הבעיה | גורמים בשורשים עם ״למה?״, השלכות בענפים עם ״ומה ההשלכה?״ | `nodes` (עומק, עמודה, סוג) | גורם אחד לפחות והשלכה אחת לפחות שנחפרו לעומק שני (שני צמתים בעמודה) |
| 3 · התבוננות והנחות | תובנות מהעץ, הנחת יסוד מאחורי כל תובנה, סיווג (מוכחת, השערה, ערכית), מקורות, והחלטה (עובדים איתה, בודקים, זונחים) | `insights` | תובנה אחת לפחות |
| 4 · נתיב קריטי | מסמנים נתיבים גורם ← תופעה ← השלכה, משווים לפי ארבעה שיקולים (נתונים, משקל, המקום שלנו, השדה), בוחרים אחד ומתעדים מה נשאר בחוץ | `paths`, `chosenPath`, `skip` | נבחר נתיב |
| 5 · הגדרת הבעיה | ממלאים את המשפט ״בגלל ש… + קורה ש… + לכן ההשלכה היא…״ ו-2 עד 4 הנחות יסוד | `def.cause/phen/cons`, `assumptions` | משפט מלא ולפחות 2 הנחות |
| לוח למליאה | מציגים, מדפיסים, שומרים כ-Word או טקסט | נגזר מהנתונים | שלבים 1, 2, 4, 5 הושלמו |

**כללים שהאפליקציה אוכפת בעדינות:** בוחרים נתיב רק בין צמתים שקיימים; נתיב שצומת שלו נמחק מסומן כלא תקין; יותר מ-4 נתיבים להשוואה לא מתאפשרים; מספר ההנחות מסומן בסגול כשהוא מחוץ לטווח 2 עד 4.

## 5. שלב 2: רעיונואות

מסך אחד, כולו נגזר מהגדרת הבעיה, שמוצגת קבועה בראשו.

1. שאלת ״איך נוכל…״, עם יצירה אוטומטית מההגדרה.
2. רעיונות. לכל רעיון מסמנים במה הוא מטפל (גורם, תופעה, השלכה) ועל איזו הנחת יסוד הוא נשען. רעיון שנשען על השערה מסומן ״דורש תיקוף״. כשכל הרעיונות מטפלים רק בהשלכה, מופיעה התראה.
3. מאמץ והשפעה בשלוש דרגות, הצבעה של כל חבר צוות, וסימון ״מועמד לפיילוט״.

שער היציאה: רעיון אחד לפחות סומן לפיילוט (`progress.pilot`).

## 7. קשר לסילבוס

כל תחנה בסילבוס יכולה להצביע על מסך במרחב שעובדים עליו בה (`station.step`). המשתתף.ת רואה בתחנה ״בתחנה הזו עובדים על: עץ הבעיה״ וכפתור שפותח את המרחב של הצוות בדיוק במסך הזה. כך המנהל.ת מתזמן.ת את התהליך על פני המסע בלי לנהל כל צוות בנפרד.

## 8. שיתוף בזמן אמת

* **הממלא.ת** הוא מי שפתח.ה ראשון.ה את המרחב. מי שנכנס.ת בהמשך הוא מסייע.ת ורואה את המסך בזמן אמת.
* **עוקבים אחרי הממלא.ת.** מסייעים נעים אוטומטית לשלב שבו הצוות נמצא, ואפשר לצאת מהמעקב ולחזור אליו.
* **הצעות.** מסייעים שולחים הצעה לשלב, בסוג מוגדר (צורך, פער, גורם חדש, העמקה, תובנה, הנחה, רעיון, הערה). הממלא.ת מוסיף.ה לרשימה, מסמן.ת כטופלה או דוחה.
* **העברת המקלדת.** כל חבר צוות יכול לקחת את תפקיד הממלא.ת, ללא אישור.
* **הצבעות** פתוחות לכל חברי הצוות, וגם הטיימר המשותף.

## 9. מודל נתונים (Firestore)

```
managers/{email}                      מנהלי קבוצות מורשים
joinCodes/{code}                      { gid, city }
groups/{gid}                          { name, city, code, ownerUid, managerEmails[], published }
  stations/{sid}                      { order, title, date, time, place, description, prep[], readings[], step }
  members/{uid}                       { name, code, joinedAt, teamId }
    progress/{sid}                    { attended, reflection, answers{} }       פרטי
  teams/{tid}                         { name, createdBy, progress{}, question, definition, ideasCount }
    roster/{uid}                      { name, at }
    meta | needs | gaps | phens | nodes | insights | paths | assumptions |
    ideas | toc | budget | funders | partners | notes | sugg | votes | live      מרחב העבודה
```

כללי האבטחה ב-`app/firestore.rules`: משתתפים קוראים את כל הצוותים בקבוצה אבל כותבים רק בצוות שהם חברים בו; יומן הנוכחות והתשובות פרטיים; הסילבוס נראה למשתתפים רק אחרי פרסום.

## 10. החלטות והנחות עבודה

* כניסת מנהלים בחשבון Google, כי כתובת מייל מאומתת היא הבסיס לרשימת ההרשאות. אין סיסמאות באפליקציה.
* משתתפים נכנסים בקוד ושם בלי הרשמה. מי שמחליף מכשיר נכנס מחדש ומקבל זהות חדשה; צריך להצטרף שוב לצוות.
* חברות בצוות היא בחירה חופשית של המשתתף.ת. המנהל.ת יכול.ה למחוק צוות ולהסיר משתתף.
* ״ממלא.ת״ הוא תפקיד חברתי ולא הרשאה: כל חבר צוות יכול לכתוב בלי אישור ברמת הכללים, והממשק הוא שמבדיל בין ממלא.ת למסייע.ת.

## 11. מה בא אחרי

1. ◻ בונה הפרזנטציה והפיצ׳ (שלב 4), שמתמלא מכל התוצרים.
2. ◻ ספריית השראה לפי קטגוריות (במוקאפ: יומן מסע + ספרייה), לכל קבוצה.
3. ◻ תצוגת מליאה למנהל.ת: לוחות הצוותים זה לצד זה.
4. ◻ מחיקת קבוצה כולל כל נתוניה, וייצוא סילבוס.
